# OLAN HIGH TECH — v24

Сайт, админ-панель и кабинет менеджеров с операторами в одном проекте.

Что изменилось в этой и прошлых версиях — в файле [CHANGELOG.md](./CHANGELOG.md).

## Быстрый старт

Нужен Node.js версии 18.18 или новее (проверить: `node -v`).

**Важно, куда положить папку проекта.** Путь должен быть коротким, без кириллицы и вне
OneDrive.

- Хорошо: `C:\dev\olan`
- Плохо: `C:\Users\Asus\Desktop\Сайт\OLAN\...` — Рабочий стол обычно синхронизируется
  с OneDrive, а тот превращает часть файлов в «облачные заглушки» и ломает установку.

```bash
npm install
```

Одна команда ставит всё. У проекта **одна** `package.json` и **один** `node_modules`
в корне — внутри `apps/` отдельных пакетов нет, разваливаться нечему.

После установки автоматически запустится проверка и напишет, всё ли в порядке.

### Запуск

Нужно **два терминала**: сервер живёт отдельно от фронтендов, чтобы их можно
было перезапускать независимо друг от друга.

**Терминал 1 — сервер:**

```bash
npm start
```

Поднимет API на http://localhost:3001. Без него не работают чат, заявки,
админ-панель и кабинет.

**Терминал 2 — сайт, админка и кабинет:**

```bash
npm run dev
```

| Что          | Адрес                 |
| ------------ | --------------------- |
| сайт         | http://localhost:5173 |
| админ-панель | http://localhost:9000 |
| кабинет      | http://localhost:9090 |

`npm run dev` сам проверяет, поднят ли сервер, и напомнит, если забыли его
запустить.

Хотите совсем раздельно — можно по одному: `npm run site`, `npm run admin`,
`npm run operator`.

В VSCode есть готовые задачи: **Terminal → Run Task → Запустить всё**.

Все команды запускаются **из корня проекта**, не из `apps/`.

### Вход

**Админ-панель** (http://localhost:9000) — логин `user`, пароль `admin1971`.
Меняется в файле `.env` (`ADMIN_USER` и `ADMIN_KEY`).

**Кабинет** (http://localhost:9090) — сюда входят менеджеры и операторы.
При первом запуске создаются двое, чтобы система сразу работала:

| Кто      | Логин      | Пароль        |
| -------- | ---------- | ------------- |
| менеджер | `manager`  | `manager1971` |
| оператор | `operator` | `operator1971`|

Их можно переименовать, сменить им пароли или удалить — всё в админ-панели,
вкладка **Сотрудники**. В `.env` учётки сотрудников больше не хранятся.

Сервер вынесен наверх, потому что обслуживает все три приложения сразу: чат на сайте,
переписку у оператора и контент в админке. Один процесс — одна общая база чатов и один
общий контент.

Внутри `apps/` намеренно нет ни `package.json`, ни `node_modules`, ни `vite.config.js`.
Всё это лежит в корне. Раньше здесь были npm workspaces, но на Windows они оказались
хрупкими: стоило одному вложенному `package.json` пропасть, и `npm install` переставал
работать целиком, выдавая `ENOENT: Could not read package.json`.

## Менеджеры и операторы

Вкладка **Сотрудники** в админ-панели.

**Менеджер** — руководитель группы. Показан карточкой, внутри неё лежат его операторы.
**Оператор** — отвечает клиентам в чате и получает заявки. Всегда привязан к менеджеру:
при создании оператора менеджер выбирается в выпадающем списке.

Создавать, переименовывать, менять пароли и удалять может **только администратор**.
Сами сотрудники свои пароли поменять не могут — пароль выдаёт админ. Смена пароля
сразу разлогинивает сотрудника на всех устройствах.

Пароль в списке скрыт точками, рядом две кнопки: глаз — показать, ключ — сменить.

### Удаление

При нажатии на корзину появляется окно подтверждения, в котором **названо имя
именно того сотрудника**, на которого нажали. Просто так ничего не удаляется.

Что происходит после удаления:

- **удалили менеджера** — его операторы случайным образом расходятся к оставшимся
  менеджерам, никто не теряется;
- **удалили оператора** — его клиенты, чаты и заявки случайным образом переходят
  к другим операторам.

## Как распределяются обращения

Сообщения из онлайн-чата и заявки с формы раздаются операторам случайно, но «липко»:
**один клиент всегда попадает к одному и тому же оператору**.

Клиент узнаётся по email и по телефону — достаточно совпадения любого из двух.

Например:

- клиент написал в чат, сообщение случайно попало к оператору **Азизу**;
  потом этот же клиент оставил заявку — она тоже уйдёт **Азизу**;
- другой клиент сначала оставил заявку, она попала к **Нигине**;
  потом он написал в чат — сообщение придёт **Нигине**.

Оператор в своём кабинете видит только свои обращения. Менеджер видит обращения
всех своих операторов и рядом с каждым — имя оператора.

Ответить в чужой чат нельзя, сервер это запрещает.

Имя оператора видно клиенту в шапке чата и **записывается буквами текущего языка
сайта**: «Нигина» по-русски, Nigina по-английски и по-узбекски. Для имён это
транслитерация, а не перевод, и работает она без интернета.

### Статусы заявок

Каждая заявка проходит три состояния: **Новая → В разработке → Обработано**.
Менять статус может только оператор, за которым закреплена заявка. В карточке
видно дату и время поступления.

### Кто что видит

| | чаты | ответ клиенту | заявки | статус заявки |
| --- | --- | --- | --- | --- |
| администратор | все | нет | все | нет |
| менеджер | своих операторов | нет | своих операторов | нет |
| оператор | свои | да | свои | да |

Переписку редактировать не может никто, кроме самого оператора — это запрещено
на сервере, а не только скрыто в интерфейсе.

### Где смотреть

**Админ-панель**, вкладка «Сотрудники» — у каждого оператора кнопки «Чаты»
и «Заявки». Открывается окно с перепиской и сводкой по заявкам.

**Кабинет менеджера** — слева список операторов, в середине чаты выбранного,
справа сама переписка. На вкладке «Заявки» слева операторы, справа сводка по
трём статусам; нажатие на любой статус раскрывает список заявок с данными
клиента и текстом обращения. Кнопка «Все операторы» показывает общую сводку.

**Кабинет оператора** — сразу свои чаты и свои заявки, без лишних списков.

## Оформление: светлая основа, тёмные вставки

Тема подстраивается под систему посетителя: тёмная в операционной системе —
тёмный сайт, светлая — светлый. Переключил человек тему кнопкой на сайте —
дальше уважается только его выбор, он сохраняется между визитами.

Тёмными остаются три блока независимо от выбранной темы:

- первый экран с радаром,
- секция мониторинга,
- галерея проектов.

Сделано это классом `dark` на обёртке в `App.jsx`: вариант `dark:` в стилях
срабатывает по вложенности, поэтому тёмная палитра включается только внутри
этих блоков. Остальная страница остаётся светлой.

Переключатель темы работает как раньше и запоминает выбор посетителя.

**Читаемость светлых блоков** доведена отдельно: бирюзовые рамки на белом
заменены на серые, полупрозрачный белый фон — на сплошной, вторичный текст
поднят с `slate-500` до `slate-600` (контраст проходит норму доступности),
бирюзовые тени заменены на нейтральные.

## Блок мониторинга на главной

Сразу после первого экрана идёт секция «Комплексы на связи»: слева
характеристики и лента фиксаций, справа радар с разворачивающимся лучом.
Тексты первого экрана остались на месте, блок добавлен под ними.

**Про ленту важно понимать одно.** Это демонстрация работы системы,
а не реальные данные с комплексов. Номера, участки и виды нарушений
собираются в браузере из уже имеющегося контента сайта — списка решений
и списка проектов, поэтому лента сама переводится вместе с сайтом.
Рядом стоит пометка «демонстрация работы», чтобы никто не принял её
за настоящие фиксации.

Когда появится настоящий поток данных, менять нужно ровно одно место —
функцию `makeEvent` в `apps/site/src/app/components/LiveMonitor.jsx`
заменить на запрос к серверу. Вся разметка останется прежней.

## Анимации

Взяты из присланного примера и переведены на палитру сайта:

- секции проявляются при прокрутке (`Reveal`);
- карточки подсвечивают верхнюю грань и приподнимаются при наведении;
- по кнопкам первого экрана пробегает блик;
- у радара крутится луч, отметки целей пульсируют;
- надпись «ЭФИР» мерцает и светится;
- фон секции мониторинга — плывущая сетка;
- цифры набегают при появлении на экране (появилось в v7).

Свечение и неон включаются только в тёмной теме: на светлом фоне такие
эффекты выглядят грязно, там остаются мягкие переходы.

Все анимации отключаются, если в системе включён запрет движения
(`prefers-reduced-motion`) — это нужно людям с вестибулярными нарушениями
и заодно экономит батарею на телефонах.

В разделах «Приборы» и «Наши проекты» есть кнопка **«Загрузить с компьютера»**.
Файл уходит на сервер, сохраняется в `apps/site/public/products/`, а в контенте

Вписать путь руками по-прежнему можно — кнопка рядом.

## Языки и перевод

Сайт работает на шести языках: русский, английский, узбекский, китайский,
арабский, украинский. Переключатель — в шапке сайта.

Языки делятся на две группы, и это главное, что стоит запомнить:

| Группа | Языки | Кто заполняет |
|---|---|---|
| Автоматические | RU, EN, UZ, UK | сервер, сам, при каждом сохранении |
| Ручные | ZH, AR | человек в админ-панели |

### Как работает автоперевод

Русский считается оригиналом. Дальше при каждом нажатии «Сохранить»
в админ-панели сервер сравнивает новый контент с прошлым и достраивает
недостающее:

- изменили русский текст — английский и узбекский обновятся сами;
- добавили карточку, продукт, вопрос в FAQ — она переведётся целиком;
- поправили руками английский или узбекский — правка останется,
  машина её не перезапишет, пока не изменится русский оригинал;
- китайский и арабский не трогаются никогда.

Если интернета у сервера нет, сохранение всё равно проходит: тексты
записываются как есть, пустые поля просто остаются пустыми и переведутся
при следующем сохранении. Русский текст никогда не подставляется вместо
перевода — иначе поле перестало бы считаться пустым.

### Кнопка «Перевести сайт»

В шапке админ-панели. Заполняет все пустые поля разом — нужна при первом
запуске и после большого объёма правок. Рядом счётчик: сколько строк ещё
без перевода.

Галочка `ZH / AR` рядом с кнопкой (видна на широком экране) добавляет
китайский и арабский в прогон. По умолчанию выключена, чтобы машинный
перевод не затёр то, что переводили вручную.

Перевод идёт **в фоне**: сервер сразу отвечает, работа продолжается
на стороне сервера, а кнопка показывает прогресс. Админкой можно
пользоваться дальше, можно даже закрыть вкладку — перевод не прервётся.
Уже заполненные поля не трогаются.

То же и с обычным сохранением: оно мгновенное, а перевод изменённых
полей уходит в фон. Поэтому надписи «Сохраняю…» на несколько минут
больше быть не должно.

### Разовый прогон из командной строки

```bash
npm run translate                     # все пустые поля, все языки
npm run translate -- --langs=uz,zh,ar # только выбранные языки
npm run translate -- --from=en        # переводить с английского
npm run translate -- --force          # перевести заново, затерев старое
```

Перед записью `siteData.js` кладётся резервная копия в
`server/data/backups`.

### Чем переводим: два пути

| | Бесплатный эндпоинт | Ключ `TRANSLATE_API_KEY` |
|---|---|---|
| Настройка | ничего не нужно | завести ключ в Google Cloud |
| С домашнего интернета | работает | работает |
| С сервера в дата-центре | **часто 403** | работает |
| Скорость всего сайта | минуты | секунды |
| Цена | бесплатно | ~2 доллара за весь сайт |

Бесплатный путь ходит на публичный адрес Google по одной строке.
Google охотно отвечает домашним и офисным адресам, но серверам хостингов
регулярно отдаёт 403 — тогда в админке будет честное сообщение
«Переводчик недоступен», а не бесконечное ожидание.

С ключом сервер переводит пачками по 100 строк через официальный
Cloud Translation API. Ключ создаётся так: Google Cloud Console →
включить Cloud Translation API → APIs & Services → Credentials →
Create credentials → API key. Положить его в `TRANSLATE_API_KEY`
(в `.env` локально или в Environment на хостинге).

**Если переводить не хочется платить** — запустите `npm run translate`
на своём компьютере, где бесплатный путь работает, и закоммитьте
получившийся `siteData.js`. Результат тот же.

### Перевод не идёт — что смотреть

В админке при ошибке показывается причина. Проверить связь вручную:

```
/api/admin/translate/check?key=ВАШ_ПАРОЛЬ
```

Ответ скажет, каким способом сервер пытается переводить и что именно
ответил переводчик.

### Перевод одного поля

В карточках есть кнопка перевода — она переводит с текущего выбранного
языка на остальные. Учитывает ту же галочку `ZH / AR`.

## Правки из админки в исходном коде

Единственный источник правды — файл `apps/site/src/app/data/siteData.js`.
Но лежит он в двух разных местах, и это важно понимать.

**На своём компьютере.** Админка пишет прямо в файл проекта. Открыли
VSCode — правка уже там. Ничего настраивать не нужно.

**На хостинге.** Папка проекта пересоздаётся при каждом деплое, поэтому
контент вынесен на постоянный диск (`SITE_DATA_FILE=/var/data/content/siteData.js`).
Сайт берёт данные оттуда, правки не теряются — но репозиторий на GitHub
остаётся со старым текстом.

Чтобы правки попадали и в код, добавьте в Render → Environment:

| Переменная | Значение |
|---|---|
| `GITHUB_TOKEN` | токен с правом `Contents: Read and write` |
| `GITHUB_REPO` | `владелец/репозиторий`, например `user/olan` |
| `GITHUB_BRANCH` | `main` |

Токен создаётся в GitHub: Settings → Developer settings → Personal access
tokens → Fine-grained tokens. Дайте доступ только к этому репозиторию.

После этого каждое сохранение в админке коммитит свежий `siteData.js`
в репозиторий. В сообщение коммита добавляется `[skip render]`, чтобы
хостинг не перезапускал сервис из-за правки текста — контент и так живёт
на диске, пересборка ради него не нужна.

В шапке админки появляется кнопка **«В код»** — ручная выгрузка на случай,
если автоматическая не прошла (например, сервер был без интернета).
Если переменные не заданы, вместо неё показывается кнопка скачивания
`siteData.js`: файл можно положить в проект руками и закоммитить.

Автокоммит отключается переменной `GIT_AUTO_PUSH=false` — кнопка при этом
продолжает работать.

Пустых коммитов не будет: если в репозитории уже лежит та же версия файла,
выгрузка пропускается.

## Контент на хостинге и контент в коде

Файл `apps/site/src/app/data/siteData.js` — единственный источник текстов.
Локально админка правит его напрямую. На хостинге он копируется на
постоянный диск (`SITE_DATA_FILE`), иначе правки пропадали бы при деплое.

Отсюда важное следствие: **деплой не перезаписывает контент на диске.**
Если в коде появился новый текст — скажем, добавили язык, — на сайт он сам
по себе не попадёт, потому что файл на диске уже существует.

Сервер разбирается с этим так. Рядом с контентом он хранит отпечаток той
версии из репозитория, с которой диск был засеян, и при каждом запуске
сравнивает три вещи: что на диске, что в коде, что было при засеве.

| Ситуация | Что делает сервер |
|---|---|
| Диска ещё нет | копирует из репозитория |
| На диске ровно то, что положил сервер, а в коде текст новее | обновляет сам |
| Контент правили в админке | не трогает, пишет подсказку в лог |

Третий случай — самый частый на живом сайте. Тогда решение за вами:
кнопка **«Обновить из кода»** в шапке админ-панели заменит контент на
версию из репозитория. Прежняя версия уходит в `server/data/backups`,
откатиться можно всегда.

Обратное направление — кнопка **«В код»**, она отправляет контент с диска
в репозиторий. Вместе они закрывают оба маршрута: из кода на сайт и обратно.

## Подписи внутри компонентов

Тексты сайта живут в двух местах, и это стоит различать:

- **контент** (продукты, решения, FAQ) — в коллекциях `siteData.js`,
  правится через админ-панель;
- **подписи интерфейса** (кнопки, заголовки блоков, подсказки) —
  в `UI_TEXT[язык]`, вкладка «Тексты сайта».

Подписи, которые встречаются прямо в разметке компонентов, собраны
в словарь `UI_TEXT[язык].s`. Ключ — русская строка:

```jsx
import { tr } from '../lib/i18n.js';

<span>{tr('Открыть карточку')}</span>
```

Так в коде виден живой текст, а не абстрактный идентификатор. Если
перевода нет, показывается русский оригинал — пропуск в словаре не
ломает страницу.

**Добавляете новую подпись** — оберните её в `tr()` и добавьте русскую
строку в `UI_TEXT.ru.s`. Остальные языки допишет автоперевод при
сохранении из админки (RU, EN, UZ, UK) либо вы сами (ZH, AR).

## Права сотрудников и чат

Роли и что им доступно в переписке:

| | читает | пишет клиенту | удаляет сообщения | шлёт файлы |
|---|---|---|---|---|
| Администратор | всё | да | да | да |
| Менеджер | своих операторов | по кнопке | по кнопке | по кнопке |
| Оператор | свои чаты | по кнопке | никогда | по кнопке |

Переключатели стоят прямо в разделе «Сотрудники», в строке каждого
человека. Зелёная кнопка — право включено, серая — выключено.

- **менеджер → «Правит чаты»** открывает сразу и запись, и удаление
  в чатах его операторов. По умолчанию выключено;
- **оператор → «Пишет»** разрешает отвечать клиенту;
- **оператор → «Файлы»** отдельно разрешает фото и документы.

Права связаны: снятое «Пишет» блокирует и файлы — без права писать
вложение всё равно не уйдёт. Снятые «Файлы» текст не трогают.

Удалять сообщения оператор не может никогда: это надзорное действие.

Закрытые возможности в кабинете не показываются вовсе — сервер отдаёт
права вместе с профилем, чтобы сотрудник не упирался в отказ уже после
набора сообщения. Но проверка стоит и на сервере: подделать интерфейс
и обойти запрет не выйдет.

### Файлы в чате

Картинки, PDF, Word, Excel, txt и zip до 10 МБ. Картинка показывается
прямо в переписке, остальное — ссылкой с названием и размером.

Вложения складываются в папку `chat-files` рядом с картинками товаров.
На хостинге ей нужен постоянный диск, иначе файлы исчезнут при деплое —
путь задаётся переменной `CHAT_UPLOAD_DIR`.

## SEO и превью ссылок

После `npm run build` запускается `scripts/seo.js`. Он подставляет в
`dist/index.html` описание, OG- и Twitter-теги, canonical и JSON-LD с данными
компании, а рядом кладёт `robots.txt` и `sitemap.xml`.

Это то, что нужно для переписки: Telegram, WhatsApp и остальные мессенджеры
при построении превью **не выполняют JavaScript**, они читают только сырой
HTML. Поэтому теги лежат прямо в файле.

Адрес боевого домена задаётся в `.env`:

```
SITE_URL=https://olan.uz
OG_IMAGE=/products/w-space.png
```

Картинку для превью лучше сделать размером 1200×630.

Запретов индексации на сайте нет: `robots.txt` открыт, в мета-тегах стоит
`index, follow`. Служебные `/admin/` и `/operator/` из индекса исключены.

Полноценный SSR пока не подключён — см. раздел «Что ещё можно сделать».

## Как связаны админка и код

Контент хранится **не** в отдельной базе. Источник правды — сам файл с данными сайта:

```
apps/site/src/app/data/siteData.js
```

Связь работает в обе стороны.

### Админка → код

Нажимаете «Сохранить» → сервер перезаписывает `siteData.js`. Добавили товар в админке —
он появился в файле. Удалили — исчез. Отредактировали — изменился.

Vite видит изменение файла и сам перезагружает открытый сайт, обновлять страницу руками
не нужно.

Что при этом сохраняется:

- стиль файла (многоязычные поля остаются в одну строку);
- функция `localize` и любой другой ваш код после блока данных — он не затирается;
- резервная копия перед каждой записью в `server/data/backups/` (последние 20).

### Код → админка

Правите `siteData.js` прямо в VSCode → сервер замечает изменение, а админка подтягивает
его сама в течение пары секунд. Перезапускать ничего не надо.

Если в этот момент в админке есть несохранённые правки, она не станет ничего молча
перетирать — покажет жёлтый баннер с выбором:

- **Взять версию из кода** — отбросить свои правки и загрузить файл;
- **Сохранить мою версию** — записать свои правки поверх файла.

### Кнопка сброса

Иконка со стрелкой в шапке админки возвращает контент к состоянию на момент первого
запуска сервера (снимок лежит в `server/data/original-content.json`).

## Работа по локальной сети

По умолчанию приложения слушают только `localhost`, и в терминале выводится одна
рабочая ссылка. Так сделано специально: раньше Vite печатал список из пяти сетевых
адресов, из которых работал только один.

Чтобы открыть сайт с телефона, узнайте IP компьютера (`ipconfig` в Windows,
`ip a` в Linux и macOS) и впишите его в `.env`:

```
VITE_HOST=192.168.1.65
```

После перезапуска в терминале появится ссылка с этим адресом:

```
http://192.168.1.65:5173     сайт
http://192.168.1.65:9000     админка
http://192.168.1.65:9090     кабинет
```

Адрес API подставляется автоматически: фронтенд берёт тот же хост, с которого его
открыли, и порт 3001.

Если с телефона не подключается — брандмауэр Windows блокирует порты 3001, 5173, 9000,
9090. Разрешите их для частной сети.

## Где держать сервер постоянно

### Render — весь проект одним сервисом (рекомендуется)

Сервер сам раздаёт сайт, админку и кабинет, поэтому Netlify не нужен:

```
https://ваш-адрес.onrender.com/           сайт
https://ваш-адрес.onrender.com/admin/     админ-панель
https://ваш-адрес.onrender.com/operator/  кабинет
```

В репозитории лежит `render.yaml` — Render прочитает его сам.
Порядок: **New → Blueprint → выбрать репозиторий**. Затем в панели задайте
`ADMIN_KEY` (пароль администратора) и `SITE_URL` (ваш адрес).

**Постоянный диск обязателен.** Папка проекта на Render пересоздаётся при
каждом деплое. Без диска пропадут переписка, созданные сотрудники,
загруженные картинки и все правки контента. В `render.yaml` диск уже описан:
1 ГБ, точка монтирования `/var/data`. Бесплатный план диска не даёт —
нужен минимум Starter.

Три переменные направляют данные на диск:

| Переменная | Значение | Что хранит |
| --- | --- | --- |
| `DATA_DIR` | `/var/data/server` | чаты, заявки, сотрудники, сессии |
| `SITE_DATA_FILE` | `/var/data/content/siteData.js` | контент сайта |
| `UPLOAD_DIR` | `/var/data/uploads` | загруженные картинки |

При первом запуске сервер копирует контент из репозитория на диск, чтобы
сайт не оказался пустым.

**Важный размен.** Когда контент живёт на диске, правки из админки больше
не попадают в `siteData.js` в репозитории — связь «админка и код» работает
только при локальной разработке. На хостинге это правильно: иначе правки
затирались бы при каждом деплое.

### Netlify — только витрина

`netlify.toml` в репозитории уже настроен: собирается сайт и генерируются
SEO-файлы, публикуется `apps/site/dist`.

Netlify раздаёт статику и **не запускает Node**. Поэтому там не будут
работать онлайн-чат, форма заявок, админ-панель и кабинет оператора —
всё это ходит в API. Подходит, если нужна только витрина для показа
и ссылок в переписке.

В **Site settings → Environment variables** задайте `SITE_URL` и `OG_IMAGE`,
иначе в превью ссылок попадёт чужой домен.

### VPS с PM2 — рекомендуемый вариант

Подходит лучше всего именно вашему проекту: контент пишется в файл, значит нужен
постоянный диск.

Недорогие хостинги: Timeweb, Beget, Selectel, Hetzner — от 3–5 $ в месяц.

```bash
# на сервере, один раз
sudo apt update && sudo apt install -y nodejs npm nginx
sudo npm install -g pm2

git clone <ваш-репозиторий> olan && cd olan
cp .env.example .env      # впишите свои пароли
npm install
npm run build

pm2 start server/index.js --name olan
pm2 save
pm2 startup               # автозапуск после перезагрузки
```

Nginx как прокси перед сервером:

```nginx
server {
    listen 80;
    server_name ваш-домен.uz;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

Бесплатный HTTPS:

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d ваш-домен.uz
```

Полезные команды PM2: `pm2 logs olan`, `pm2 restart olan`, `pm2 status`.

### Railway, Render, Fly.io

Деплой прямо из GitHub, без настройки Linux. Но есть важная оговорка: файловая система
там эфемерная, а ваш контент лежит в `siteData.js`. При каждом передеплое правки из
админки откатятся к тому, что в репозитории.

Лечится одним из двух:

- подключить постоянный диск (persistent volume) и указать на него `SITE_DATA_FILE`;
- либо принять, что контент правится в коде и коммитится в репозиторий.

### Свой компьютер или мини-ПК в офисе

Бесплатно, но нужен статический IP либо туннель (Cloudflare Tunnel — бесплатный),
и машина должна быть всегда включена.

### Обычный shared-хостинг

Не подойдёт: нужен постоянно работающий процесс Node, а не только раздача файлов.

## Переменные окружения

Файл `.env` в корне, общий для сервера и всех фронтендов.

| Переменная       | По умолчанию                         | Назначение                          |
| ---------------- | ------------------------------------ | ----------------------------------- |
| `PORT`           | `3001`                               | порт API-сервера                    |
| `ADMIN_USER`     | `user`                               | логин администратора                |
| `ADMIN_KEY`      | `admin1971`                          | пароль администратора               |
| `OPERATOR_USER`  | `user`                               | логин оператора                     |
| `OPERATOR_KEY`   | `adminOper`                          | пароль оператора                    |
| `VITE_API_URL`   | определяется сам                     | адрес API, если он на другой машине |
| `SITE_DATA_FILE` | `apps/site/src/app/data/siteData.js` | путь к файлу контента               |

Перед выкладкой в интернет обязательно смените пароли.

## Что ещё можно сделать

**Полноценный SSR/SSG.** Сейчас страницы собираются в браузере, а мета-теги
для поисковиков и мессенджеров лежат в HTML статически — этого достаточно
для превью ссылок и для индексации Google, который выполняет JavaScript.

Настоящий серверный рендеринг потребует переезда на Next.js или Astro:
текущая структура с ленивой загрузкой компонентов не рендерится на сервере
как есть. Это отдельная работа, а не правка в пару файлов. Смысл в ней
появляется, если важны Яндекс (он хуже работает с JavaScript) или скорость
первой отрисовки на слабых телефонах.

## Если что-то пошло не так

Первым делом:

```bash
npm run check
```

Скрипт проверит версию Node, целостность файлов проекта, полноту установленных пакетов
и файл контента, после чего скажет по-русски, что именно сломано и как чинить.

### Частые случаи

**`Could not resolve "./icons/earth.js"`** — пакет `lucide-react` установился не
полностью. В нём около 1500 мелких файлов, и распаковку часто обрывает антивирус или
OneDrive. Лечится командой `npm run reinstall`. Если повторяется — перенесите проект
в `C:\dev\olan` и добавьте папку в исключения антивируса.

**`ENOENT: Could not read package.json`** — вы запустили npm не из корня проекта, либо
файл действительно удалён. Проверьте `npm run check`. Никогда не удаляйте файлы вручную
командой `Remove-Item` — для очистки есть `npm run clean`, он трогает только
`node_modules` и сборки.

**Админка пишет «Сервер недоступен»** — не запущен `npm run server`.

**Порт занят** — измените `PORT` в `.env` для сервера или порт в соответствующем
`vite.*.config.js` для фронтенда.

**Контент не сохраняется** — посмотрите логи сервера. Проверьте, что `siteData.js` не
заблокирован другой программой и что есть права на запись.

**Сломался `siteData.js`** — возьмите рабочую копию из `server/data/backups/`, там
последние 20 версий с датой в имени файла.
